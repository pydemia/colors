## 목표와 확정 요구

Colors는 기준색, 콘셉트, 사진에서 팔레트를 만들고 실제 사용처에 맞게
색의 역할을 배정하는 웹 도구다. 사용자는 결과를 사이트, 발행물,
PowerPoint, 코드 편집기, 터미널에서 미리 보고 가져갈 수 있어야 한다.

사용자가 요청한 범위는 다음과 같다.

- 테마와 추구하는 콘셉트에 따른 팔레트 생성
- 한 색상에서 단색, 유사색, 보색, 분할 보색, 삼각 배색 등 조화 유형 선택
- 사진 업로드와 인터넷에서 찾은 사진을 통한 팔레트 추출
- 사진의 지점을 직접 골라 색을 추출하고 자동 추출 결과를 수정
- 사이트, 발행물, PowerPoint의 색조와 색상 조합 설계
- VS Code, JetBrains IDE, Vim의 구문 강조 색상 설계
- iTerm2, Windows Terminal, PuTTY의 터미널 색상 설계
- 웹사이트에 게시하여 브라우저에서 사용

위 목록은 전체 제품 범위다. 첫 공개 버전과 후속 출시의 권장 순서는
아래에 적었다. 단계 구분은 대상 프로그램을 제품 범위에서 제외하지 않는다.

## 사용자 흐름 제안

세 가지 시작 경로를 같은 편집 화면으로 모은다.

1. 콘셉트: 사용처, 분위기, 명도, 채도, 피할 색을 입력한다.
2. 기준색: HEX 또는 색상 선택기로 입력하고 조화 유형을 고른다.
3. 사진: 업로드하거나 후속 단계의 검색 결과를 선택한다. 자동 추출 색과
   사용자가 찍은 지점의 색을 함께 편집한다.

이후 후보 팔레트 비교 → 색상 고정·교체·순서 조정 → 용도별 역할 배정
→ 시안·대비 확인 → 저장·공유·내보내기 순서로 진행한다. 사진의
자동 추출색과 직접 고른 색은 출처를 구분해서 표시한다.

후속 단계에서 검색 사진 URL을 불러올 수 없는 경우를 빈 팔레트로 처리하지 않는다.
접근 실패, 허용되지 않은 형식, 이미지 해독 실패를 구분해 안내한다.
인터넷 이미지 검색의 제공처, 이용 조건, 원본 보관 정책은 미정이다.

## 팔레트와 생성 규칙 제안

원본 팔레트에는 사용자가 입력하거나 고정한 색, 추출 출처,
조화 유형, 조정 이력을 남긴다. 사이트·문서·코드·터미널의
역할 색상은 원본에서 파생한다. 파생색을 바꿔도 원본의 고정색이
조용히 바뀌지 않도록 한다.

- 조화 유형: 단색, 유사색, 보색, 분할 보색, 삼각, 사각 배색
- 명도·채도 조정: OKLCH 기반 후보를 만들되 출력 색역을 확인
- 후보 정렬: 동일 입력에 안정적인 순서를 사용하고 동점 기준을 명시
- 충돌 검사: 비슷해서 구분하기 어려운 색과 낮은 대비를 표시
- AI의 역할: 자유 문장에서 조건을 추출하거나 후보 설명을 돕는
  방안을 검토한다. 최종 HEX 값은 사용자가 확인·수정할 수 있어야 한다.

첫 구현의 기본 색상 수·조화 각도·후보 수는 아래 권장값으로 시작하고,
대표 사례 평가에서 조정한다. 평가 가중치와 생성 모델 도입은 검증 후
결정한다. 검증되지 않은 생성 품질을 보장하지 않는다.

## 용도별 색상 역할

| 용도 | 필요한 역할과 미리보기 |
| --- | --- |
| 웹사이트 | 텍스트, 배경, 주·보조·강조색, 링크, 상태색; 실제 페이지 시안 |
| 문서·PowerPoint | 텍스트·배경·강조·하이퍼링크; 표·도형·슬라이드 시안 |
| 발행물 | 표지·본문·강조색; 인쇄를 요구하면 출력 조건별 색상 검토 |
| 코드 편집기 | 배경, 기본 텍스트, 주석, 키워드, 문자열, 수, 타입, 함수, 변수, 오류, 경고, 선택 영역 |
| 터미널 | 전경·배경, 커서·선택 영역, ANSI 기본 8색과 밝은 8색 |

PowerPoint 테마에는 텍스트·배경 4색, 강조 6색, 하이퍼링크
2색이 있다.
[Microsoft PowerPoint 문서](https://support.microsoft.com/en-us/powerpoint/create-your-own-theme-in-powerpoint).

iTerm2·Windows Terminal·PuTTY는 터미널 색상을 설정한다. Vim의
구문 강조는 Vim 색상 설정과 터미널의 색상 처리 능력에 따라
보이는 결과가 달라질 수 있다. 따라서 터미널 시안에는 Vim 실행
예시와 ANSI 색상표를 함께 둔다.

인쇄 결과는 화면의 HEX만으로 보장하지 않는다. 인쇄 출력까지
제공하려면 대상 인쇄 조건과 ICC 프로파일을 정해야 한다.
[Adobe 색상 관리 문서](https://helpx.adobe.com/photoshop/using/color-managing-documents--printing.html).

## 품질과 검증 기준

- 고정한 기준색은 생성·역할 배정·내보내기 과정에서 정확히 유지한다.
- 자동 추출색, 직접 찍은 색, 생성한 색의 출처를 구분한다.
- 텍스트와 실제 배경의 대비를 계산하고 미달 조합을 표시한다.
  웹의 일반 텍스트 WCAG AA 기준은 4.5:1이다.
- 색각 차이를 고려한 미리보기와 색상 외 구분 수단을 검토한다.
- 사용자 파일은 형식 검사뿐 아니라 대상 프로그램에서 가져와 확인한다.
- 인터넷 사진의 접근 실패나 권한 문제를 명시하고 임의 색상으로
  성공한 듯 대체하지 않는다.
- 같은 입력·설정에서 순서가 안정적인 후보를 생성한다. AI를 사용해
  비결정성이 생긴다면 그 경계를 사용자에게 드러낸다.

접근성 참고:
[WCAG 2.2](https://www.w3.org/TR/wcag/).

### 출시 순서와 완료 조건 — 권장

| 단계 | 사용자에게 제공할 결과 | 단계 종료 조건 |
| --- | --- | --- |
| 1. 첫 공개 | 콘셉트·HEX → 5색 팔레트와 후보 3개 → 색 잠금·수정 → 모든 사용처 시안과 역할 배정 → 대비 표시 → 기기 안 저장·JSON/CSS | 잠금·출처·역할 보존, 저장·재열기, 파일 왕복, 데스크톱·모바일 흐름, 배포 URL 확인 |
| 2. 사진·공유 | 사진 업로드·파일 저장소·다운로드 정책, 공식 제공처 검색, 자동·직접 추출, 선택적 계정·비공개 동기화·공개 읽기 링크 | API 약관 준수, 이미지 픽셀 접근, 파일 보관·삭제·공개 범위 확인 |

| 4. 고급 기능 | 공개 갤러리, AI 콘셉트 해석, 인쇄용 색상 관리 | 사용성·생성 품질·권리·인쇄 조건 검증 |

모든 사용처는 첫 단계에서 역할 설계와 시안을 갖는다. 전용 파일 제공 시점은
가져오기 검증에 따라 달라진다. 첫 단계의 코드 시안은 최소 두 언어의
같은 예제를, 터미널 시안은 ANSI 16색과 기본 전경·배경을 보여 준다.

### 생성 입력·데이터 계약 — 권장

- 콘셉트 입력: 사용처(복수 선택), 분위기 태그 최대 3개, 색 방향
  (따뜻함·차가움·중립·상관없음), 밝기(밝음·중간·어두움),
  채도(차분·중간·선명), 피할 색(선택), 자유 메모(선택). 자유 메모는
  첫 단계에서 생성 조건으로 해석하지 않는다고 UI에 표시한다.
- 콘셉트 생성은 버전이 있는 초기 색 목록에서 색 방향과 분위기 태그에
  맞는 기준 hue를 정하고, 밝기·채도로 OKLCH 범위를 좁힌 뒤 조화 규칙을
  적용한다. 태그별 hue 연결은 사람이 편집 가능한 설정으로 두고 대표 사례
  평가에서 조정한다. 사용처는 색 자체보다 역할 배정과 대비 검사에 반영한다.
  충돌하는 태그는 입력 순서를 우선순위로 삼고 사용자가 기준색을 바꿀 수 있다.
- 기준색 입력: `#RRGGBB` 한 색과 조화 유형. 첫 기본안은 단색·유사색·보색·
  분할 보색·삼각·사각 배색, 5색 팔레트, 후보 3개다. 유사색은 기준 hue의
  ±30°·±60°, 보색은 180°, 분할 보색은 ±150°, 삼각은 ±120°, 사각은
  90° 간격을 출발점으로 둔다. 필요한 색은 명도를 달리해 채운다.
- 사진 입력: 첫 단계에서는 PNG·JPEG·WebP 업로드를 우선 검토하고, 자동 추출
  5색과 사용자가 찍은 지점의 원본 픽셀색을 별도 표시한다. 크기·픽셀 수 상한,
  방향 보정, 투명 픽셀 처리와 색상 프로파일 변환은 구현 전에 테스트 사례로 정한다.
- 후보는 OKLCH에서 만들되 sRGB 색역 밖이면 채도를 줄여 수렴한다. 입력·잠금·
  직접 고른 픽셀의 기준값은 정규화한 `#RRGGBB` sRGB로 보존한다. 생성 버전과
  규칙 입력을 저장해 같은 입력에서 후보 순서가 재현되도록 한다. 첫 단계의
  후보 순서는 고정된 조화 규칙 순서로 정하고 검증 전의 '품질 점수'를 붙이지 않는다.
- 프로젝트 JSON의 최상위 필드: `schemaVersion`, `projectId`, `source`,
  `generatorVersion`, `swatches`, `roleSets`, `updatedAt`. 각 swatch에는
  `id`, `hex`, `origin`(입력·자동 추출·직접 선택·생성), `locked`,
  사진 출처가 있을 때 `imageSourceId`와 선택 좌표를 둔다. 사진 자체는
  기본 저장하지 않고 출처 이름·링크·제공처·권리 정보를 메타데이터로 둔다.
- 역할 값은 swatch `id`를 참조한다. 파생색이 필요하면 `overrideHex`와
  수정 이유를 별도로 기록한다. 원본색 수정은 참조 역할만 다시 계산하고
  덮어쓴 역할은 유지한다. 잠긴 swatch 수정은 명시적 잠금 해제 후 가능하다.
  내보내기는 현재 역할값의 스냅샷을 만들며 프로젝트 원본을 바꾸지 않는다.
- `roleSets`는 `web`, `publication`, `powerPoint`, `editor`, `terminal`을
  분리한다. 예를 들어 `roleSets.web.text`는 `{ "swatchId": "s1",
  "overrideHex": null }`로 저장한다. `editor`에는 구문 역할,
  `terminal`에는 ANSI 16색 역할을 각각 두며 둘 사이를 자동 동기화하지 않는다.
- 자동 생성이 대비를 맞추기 위해 잠긴 기준색을 변경해야 할 때는 해당
  조합을 미달로 표시하고, 배경 또는 다른 비잠금 역할의 수정안을 제시한다.

### 화면 흐름·판정 기준 — 권장

1. 시작 화면에서 세 경로 중 하나를 고르고 입력을 검증한다.
2. 같은 편집 화면에서 후보 3개를 비교하고 색 출처·잠금을 확인한다.
3. 용도 탭에서 역할을 배정한다. 웹·발행물·슬라이드·코드·터미널 탭은
   원본 팔레트를 공유하고 각자 덮어쓰기를 가진다.
4. 시안에 적용된 전경·배경의 대비를 계산한다. 웹 일반 텍스트 4.5:1,
   큰 텍스트 3:1, 의미 있는 UI 요소 3:1을 기준으로 표시한다.
   편집기·터미널에는 같은 수치를 가독성 목표로 표시하되 WCAG 적합성
   인증처럼 표현하지 않는다.
5. 저장·내보내기에서 파일 형식과 실제 검증된 적용 대상을 구분해 보인다.
   기기 안 저장은 브라우저 데이터 삭제 시 사라질 수 있음을 알리고
   프로젝트 JSON 백업을 권한다.

완료 판정 사례: 잠근 `#336699`는 후보 재생성·역할 배정·JSON 왕복 후에도
동일해야 한다. 사진에서 직접 고른 색은 자동 추출색과 출처가 달라야 한다.
한 역할의 덮어쓰기는 다른 용도 역할과 원본 swatch를 바꾸지 않아야 한다.
대비 미달 조합은 해당 시안 위치와 수치가 일치해야 한다.

### 인터넷 사진·저장 정책 — 권장

- 첫 단계에서 업로드 사진은 브라우저 안에서 처리하고 원본을 서버에 보내거나
  프로젝트 파일에 포함하지 않는다. 새로 열 때는 추출색과 출처 메타데이터는
  남지만 사진 미리보기·재채점은 원본 재선택이 필요하다고 안내한다.
- 두 번째 단계에서 Unsplash API를 우선 검토한다. API로 표시한 사진에는
  사진가·Unsplash 출처와 프로필 링크를 넣고 제공처의 이미지 URL·이용 조건을
  따른다. 검색 결과의 원본 이미지는 기본 보관하지 않는다. API 키는
  브라우저에 노출하지 않고 서버 측에 둔다.
- 검색 결과를 브라우저에서 픽셀로 읽을 수 있는지 CORS를 실제 확인한다.
  실패하면 추출 실패 이유와 업로드 대안을 보여 준다. 임의 URL을 서버가
  대신 읽는 기능은 별도 보안 설계와 권리 검토 후 결정한다.
- 공개 링크·갤러리를 추가할 때는 비공개가 기본이고 게시를 따로 선택한다.
  저장 데이터의 삭제·비공개 전환·보관 기간과 사진 메타데이터 공개 범위를
  먼저 명세한다.

### 내보내기 검증 행렬 — 전부 미실행

| 대상 | 만들 최소 산출물·적용 방식의 권장안 | 실제 확인할 항목 |
| --- | --- | --- |
| 범용 | 버전 있는 프로젝트 JSON, `:root` CSS 변수 | 다시 읽을 때 잠금·출처·역할 보존; CSS 시안 일치 |
| PowerPoint | 12개 테마 색상 슬롯에 매핑한 `.thmx` 후보 | Windows·Mac의 대상 버전에서 테마 적용과 재열기; 기존 슬라이드 대비 |
| VS Code | 첫 단계는 사용자 설정 조각, 후속은 색상·TextMate·semantic token 규칙이 든 테마 확장 | 설정 적용, 확장 설치, 최소 두 언어와 semantic token 미리보기 |
| JetBrains | 편집기 `.icls` | 대상 IDE에서 가져오기·재시작·구문색 확인; 창 전체 UI는 별도 |
| Vim | `colors/<이름>.vim` | `:colorscheme` 적용, truecolor와 제한 색상 환경 |
| iTerm2 | `.itermcolors` | 프로필 색상 프리셋 가져오기, ANSI 16색·커서·선택 영역 |
| Windows Terminal | `schemes` 배열에 넣을 JSON 조각과 프로필 연결 안내 | 기존 `settings.json` 유지, 색상표 적용·재시작 |
| PuTTY | 세션 색상별 RGB 표와 수동 적용 안내; `.reg`는 보류 | 세션 저장·재열기, ANSI 16색, 다른 세션·설정 보존 |

공식 문서에서 **형식·설정 경로만 확인**했다. `.thmx`는 PowerPoint 테마,
VS Code 테마 JSON은 확장 기능에 포함하는 방식, `.icls`는 JetBrains 편집기
색상표, `.itermcolors`는 iTerm2 색상 프리셋이다. Windows Terminal은
`settings.json`의 `schemes`를 사용한다. PuTTY는 Windows에서 저장 세션을
레지스트리에 둔다. 이 사실이 Colors가 만든 파일의 정상 적용을 뜻하지 않는다.

### 프롬프트·생성 평가 계획 — 미실행

콘셉트 6개(밝은 공공 서비스, 어두운 개발 도구, 차분한 보고서,
선명한 행사 홍보, 사진 기반 여행, 잠긴 브랜드색)를 준비한다. 각 사례의
사용처·밝기·채도·금지색을 고정한다. 구조화 입력만 사용하는 규칙 생성과
프롬프트 표현 3종을 비교하고, 각 프롬프트는 같은 모델·버전·설정에서
3회 실행한다. 색 제약 준수,
잠금 보존, 역할 적합성, 대비 미달 수, 후보 간 차이, 사용자의 수정량을
기록한다. 평가 전 기준과 원본 결과를 함께 보존한다. 실험 전까지
프롬프트 방식의 우수성이나 AI 도입 효과를 주장하지 않는다.

## 남은 결정과 다음 작업

첫 공개 범위를 구체화한 [프로젝트 데이터 계약](DATA_CONTRACT.md),
[잠긴 기준색 JSON 예제](examples/locked-base-color.json),
[화면 와이어프레임](WIREFRAMES.md)을 작성했다. 데이터 예제의 색값은
설명용이며 생성 품질이나 대비 적합성을 검증한 값이 아니다.

제품 소유자가 결정할 사항은 첫 공개 범위의 승인, 공개 링크·갤러리의
필요성, 도메인·배포 계정, 인쇄용 기능의 사업상 우선순위다. 구현 전에는
사진 상한·색상 프로파일, 조화 규칙의 실제 결과, API 약관과 픽셀 접근,
각 프로그램의 대상 버전과 가져오기 절차를 실험으로 정한다.

권장 진행 순서: 데이터 계약·와이어프레임 검토 → 대표 입력의 규칙
생성·프롬프트 평가 → 첫 단계 구현 → 범용 출력 왕복·접근성 검사 →
프로그램별 최소 파일 생성과 실제 가져오기 → 검증된 출력부터 공개.

실제 구현, 고충실도 UI 시안, 프롬프트 결과 비교, 파일 가져오기 검증,
사이트 게시·배포는 아직 하지 않았다.
