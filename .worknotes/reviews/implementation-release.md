다만 R15/R13 복원 경계의 O1과 저장 경계 O2/O3는 출시 전에 닫아야 한다.

## O1 — 필수 장면 데이터가 빠진 JSON을 허용하여 표시 경로가 실패함

- 중요도/시점: 높음, 출시 전 수정. 유형: 실행으로 확인한 파서 계약 결함.
- 근거: snapshot `project.ts:715`–`:719`는 scene의 id/name만 자체 검사한 뒤
  `parseProject({...value, ...scene, sequence: []})`를 호출한다. 빠진 swatches/
  roleSets/studio는 부모 value에서 보충된다. 반환값은 원래 scene에 반영하지
  않는다. `StudioPanels.tsx:330`–`:334`는 저장된 각 scene의 swatches를 직접
  순회하고 scene의 studio/roleSets를 그대로 불러온다. `App.tsx:1150`에서
  이 컴포넌트가 활성 프로젝트와 함께 렌더링된다.
- 재현: 정상 schema2 프로젝트의 sequence를
  `[{id: 'missing-required-scene-fields', name: 'incomplete'}]`로 바꿔
  `parseProject(exportProject(project))` 실행. 파서가 성공했고 반환 scene의
  키는 id/name뿐이었다. 실제 렌더링 식 `scene.swatches.map(...)`을 실행하면
  `Cannot read properties of undefined (reading 'map')`가 발생했다.
- 실패조건 → 영향: 필수 장면 필드 누락 JSON 가져오기 → 부모의 값으로
  가짜 유효성 통과 → 가져오기 성공 후 장면 목록 렌더링 오류 또는 장면
  불러오기에서 undefined 프로젝트 상태. 정상 프로젝트를 유지하며 오류를
  알리는 R15 경계를 벗어난다. 브라우저 전체 crash 화면은 이번에 실행하지
  않았으며 파서/렌더링 식 오류는 직접 실행했다.
- 반증: 각 장면에 대해 재귀 parseProject를 호출한다는 보호장치는 존재한다.
  실제로 제공된 잘못된 색/역할/Studio 값 일부를 검사하지만, 필드 자체의
  누락을 부모 기본값으로 숨긴다. 현재 단위 테스트의 JSON 왕복과 e2e의
  sequence 길이 확인은 이런 불완전한 장면을 검사하지 않는다.
- 최소 수정: 장면 swatches/roleSets/studio를 필수로 검사하고 별도 scene
  계약으로 검증한다. 필요하면 top-level 메타데이터만 명시적으로 붙인
  검증용 프로젝트를 만들고, 정규화된 반환값의 장면 필드도 저장한다.
- 수용 기준: 세 필드 각각의 누락/타입 오류와 끊어진 장면 역할 참조를
  가져오기 전에 거부한다. 현재 편집 프로젝트가 그대로 남고 오류 위치를
  알린다. 정상 1–5장면의 JSON 왕복·재순서·복원·CSS 출력은 보존한다.

## O2 — 삭제 경로의 schema1→2 이행은 원본 백업을 우회함

- 중요도/시점: 중간, 첫 이행 배포 전 수정. 유형: 실행으로 확인한 저장 경로 차이.
- 근거: snapshot `project.ts:723`–`:734`는 schema1 항목을 메모리에서 schema2로
  이행한다. `saveProject:742`–`:744`는 기존 원문을 v1.backup에 먼저 보존한다.
  `deleteProject:756`–`:760`은 같은 이행된 목록을 저장하면서 백업하지 않는다.
  `App.tsx:649`–`:658`의 저장 목록 삭제는 활성 프로젝트 없이도 실행할 수 있다.
- 재현: schema1 예제 두 프로젝트를 `colors.projects.v1`에 넣고 새 앱에서
  첫 쓰기 동작으로 한 프로젝트를 삭제. 남은 항목의 schemaVersion은 2가
  됐지만 `colors.projects.v1.backup`은 생성되지 않았다.
- 실패조건 → 영향: 기존 사용자가 팔레트를 새로 열거나 저장하기 전에
  저장 목록을 정리 → 나머지 프로젝트 이행이 원본 보존을 건너뜀 → 이전
  schema1 전용 코드로 복귀하거나 이행 전 파일이 필요할 때 원문 복원 경로
  상실. 삭제한 항목 자체를 복구하라는 새 요구가 아니라 남은 데이터의
  이행 전 보존 정책에 관한 문제다.
- 반증: saveProject의 선행 백업은 유효하며 저장 실패 시 원본 덮어쓰기를
  막는다. 그러나 삭제는 별도 setItem 경로여서 이 보호장치를 호출하지 않는다.
  현재 저장/삭제 테스트는 신규 schema2 데이터만 사용한다.
- 최소 수정: 이행된 저장소를 쓰는 경로의 백업/검증/쓰기 정책을 공통화한다.
  기존 원문 백업이 성공하기 전에 schema1 저장소를 schema2로 덮어쓰지 않는다.
- 수용 기준: schema1 복수 프로젝트에서 첫 동작이 삭제일 때도 원문 백업이
  생기고 남은 프로젝트의 ID/잠금/색/override가 보존된다. 백업 쓰기 실패 시
  기존 저장 키가 바뀌지 않는다. 실제 복구 정책은 출시 기록에서 설명한다.

## O3 — 자동 저장 대기 중 프로젝트를 전환하면 마지막 수정을 잃을 수 있음

- 중요도/시점: 중간, 출시 전 수정 또는 동등한 보호 검증. 유형: 코드로 확인한
  조건부 경합; 실제 브라우저에서 시간 경계를 재현하지는 않았다.
- 근거: snapshot `App.tsx:387`–`:398`은 변경 후 400ms timer로 저장하고
  project 변경 시 그 timer를 취소한다. 저장 프로젝트 열기 `:620`–`:624`,
  JSON 전환 `:538`, 새 생성 `:462`는 현재 프로젝트의 pending 저장을 먼저
  완료하지 않고 setProject한다. JSON 전환 확인 문구 `:534`는 현재 프로젝트가
  기기에 저장된다고 설명한다.
- 구체 시나리오: 프로젝트 A/B를 저장해 둔 상태에서 A의 역할 HEX를 변경하고
  400ms 안에 B를 연다. A의 새 저장 timer가 cleanup으로 취소되고 B만 이후
  저장된다. A를 다시 열면 최근 역할 변경 대신 이전 값이 남을 수 있다.
  JSON 가져오기 확인도 저장 성공을 보장하지 않는 경로다.
- 반증: ‘이 기기에 저장’은 동기 저장하며 e2e의 저장 재열기 테스트는 이
  버튼을 누른다. 그러나 자동 저장만 사용하는 빠른 전환은 검사하지 않는다.
  새 프로젝트를 저장하는 timer가 취소된 이전 project의 수정을 저장하지 않는다.
- 최소 수정: 프로젝트 전환 전에 pending 상태를 flush하거나, timer cleanup의
  정책을 작업 취소와 저장소 반영에 맞게 분리한다. 저장 실패 시 전환/백업
  정책을 정하고 성공하지 않은 저장을 성공한 듯 안내하지 않는다.
- 수용 기준: 가짜 timer 또는 실제 브라우저에서 0–399ms 전환 사례를 확인한다.
  A 수정 직후 B 열기/JSON 가져오기/새 생성 후 A를 다시 열면 수정값이 남는다.
  quota 실패에서도 현재 작업을 JSON으로 보관할 수 있고 실패를 표시한다.

## O4 — 선택한 표색계가 저장/재개되지 않음

- 중요도/시점: 중간, R15 완료 판정 전에 구현 또는 명시적 판정.
  유형: 코드로 확인한 지속성 계약 누락.
- 근거: 공통 개선 검토 `COLOR_IMPROVEMENT_REVIEW.md:223`은 프로젝트에
  editingSpace를 저장하도록 제안하고 `:225`는 저장·재개에서 설정 보존을
  완료 조건으로 둔다. snapshot 명세 R15는 모든 설정 복원이다.
  `StudioPanels.tsx:176`은 표색계 mode를 `useState('oklch')`로만 갖고,
  선택 `:225`–`:226`은 setMode만 호출한다. `studio.ts:24`–`:48`의 Studio와
  프로젝트 직렬화에는 editingSpace가 없다.
- 구체 시나리오/영향: Lab 또는 HSV로 표시/편집 체계를 바꾸고 JSON을 받거나
  기기에 저장 → 앱 재열기/JSON 복원 → ColorAnalysis가 OKLCH 기본값으로
  돌아온다. 색 자체는 그대로지만 선택했던 편집 조건이 복원되지 않는다.
  브라우저 재개 실행은 이번 리뷰에서 수행하지 않았으며 상태/직렬화 경로를
  직접 읽어 확인했다.
- 반증: 표색계 전환에서 원색을 바꾸지 않는 것은 올바르다. 그것과 사용자가
  선택한 표기 체계를 프로젝트 메타데이터로 저장하는 것은 양립할 수 있다.
  현재 e2e는 선택 직후 원본 HEX 보존만 확인하고 재개를 검사하지 않는다.
- 최소 수정/수용 기준: 선택한 좌표 체계를 프로젝트 설정에 넣고 schema1 및
  해당 필드 없는 이전 schema2 입력에는 기본값을 제공한다. 모든 제공 체계를
  바꿔 저장/복원해 표시 체계와 색값이 함께 보존되는지 확인한다. 조정자가
  단순 임시 뷰 상태로 판단한다면 R15/공통 검토와의 차이를 완료 기록에 남긴다.

## 실행으로 확인한 보호장치와 제외한 의심

- web primary=`#123456`, PowerPoint accent1=`#234567`, editor comment=`#345678`,
  terminal magenta=`#456789`로 서로 다르게 수정한 fixture에서 CSS, DTCG,
  Tailwind4, Office XML, VS Code, Windows Terminal 출력값이 모두 일치했다.
- ASE의 RGB block, Office의 12슬롯, CUBE의 red-fastest 순서 및 sRGB
  설명은 코드와 테스트에 있다. 이를 실제 대상 앱에서 가져온 결과로 해석하지 않았다.
- CSV는 sampleMap의 충돌 검사 후에만 다운로드하며 모든 stop t를 표본에
  포함한다. JSON 프로젝트 백업이 유효한 작업상의 colormap 충돌을 저장하는
  것은 오류로 세지 않았다.
- Office는 `.clrScheme.xml`이며 완전한 `.thmx`라고 표시하지 않는다.
  실제 가져오기 미검증 안내가 있으므로 그 자체를 허위 호환성 결함으로 세지 않았다.
- 검토용 혼합 모델과 LUT가 물리적 물감/카메라 LOG라고 주장하는 의심도
  UI의 근사/색공간 설명으로 반증했다.
- 손상/미래 schema 항목 하나가 있으면 정상 저장 목록의 load/save 모두
  실패하는 것도 재현했다. 기존 데이터는 덮어쓰지 않지만 앱 내 복구/원문
  백업 경로는 없다. O1/O2 수정 및 운영 복구 검증 때 확인할 경계로 남기며
  임의로 ‘손상 데이터 자동 복원’이라는 새 필수 기능을 추가하지 않는다.
