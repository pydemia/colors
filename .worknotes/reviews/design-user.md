## U1 — 추천 조건 변경이 적용 결과를 바꿔도 되는지 서로 다른 계약

우선순위: P1. 근거 확실성: 높음.

**근거:** 명세 50–53행은 설정 변화가 즉시 후보와 역할에 반영된다고 한다.
검토 문서 286행은 checkbox 변경 시 추천을 갱신하거나 재추천 상태를 알리되
현재 적용 결과를 자동으로 덮어쓰지 않는다고 한다. 검토 문서 199행도
색상환 표시 변경과 기존 팔레트 적용을 구분한다.

**실패 조건 → 영향:** 사용자가 후보를 적용해 역할과 출력을 확인한 뒤
다른 추천을 탐색하려고 색 고정을 해제하거나 색상환을 변경한다.
50행을 모든 설정에 그대로 적용하면 미채택 후보의 파생 역할이 현재
프로젝트에 들어간다. 사용자는 후보를 비교하기 전에 적용색을 잃고,
‘출력은 현재 보이는 프로젝트’라는 계약만으로는 변경 의도를 알 수 없다.

**기존 보호장치 반증:** 51–52행의 수동 역할 유지 및 고정 HEX 보존은
직접 수정한 값과 고정색만 보호한다. 채택한 후보의 유연색·자동 역할은
보호하지 않는다. 기존 `choose()`의 명시적 적용 버튼
(`src/App.tsx:496`, `1040`)도 설정 변경의 즉시 적용 정책을 해결하지 않는다.

**최소 수정:** 설정을 둘로 명시한다. 고정/보정 한계/조화/추천 의도/색상환의
생성 모델 변경은 후보 또는 ‘재추천 필요’ 상태만 갱신하며 채택 결과는
유지한다. 사용자가 명시적으로 현재 결과를 편집하는 컬러리스트 조작·역할
편집은 즉시 반영할 수 있다. 좌표 표기와 색상환 보기만 전환하는 동작은
색값을 변경하지 않는다. 후보 적용 때만 채택 결과와 자동 역할을 교체한다.
Project 안에 조건·미채택 후보·채택 결과를 구별할 수 있어야 하며,
이를 별도의 독립 원본으로 분리할 필요는 없다.

**검증 기준:** 후보 B 적용 → 고정 OFF/추천 모델 변경 → 후보 변화 확인 →
적용 결과와 역할/출력 HEX 불변 → 새 후보 적용 → 그때 역할/출력 갱신.
좌표 표기 전환과 색상환 보기 전환의 전후 HEX도 같아야 한다.

## U2 — 결과 편집 후에도 후보 카드가 ‘선택됨’으로 남는 상태

우선순위: P2. 근거 확실성: 중간(기존 구조를 계승할 경우).

**근거:** 명세 47–53행은 후보 비교와 현재 프로젝트 편집을 같은 REFINE에
둔다. 기존 `src/App.tsx:381`의 `selectedCandidate`는 후보 인덱스이며,
`apply()`(432–447행)의 색/잠금/역할 변경에서 갱신되지 않는다.
1045–1055행의 ‘선택됨’과 `aria-pressed`는 인덱스만 따른다.

**실패 조건 → 영향:** 후보 2를 적용하고 색 하나를 원본으로 되돌리거나
현재 결과를 직접 보정한다. 카드의 색과 실제 프로젝트가 달라져도
‘선택됨’이 남으면 사용자는 카드의 원색/추천색 비교가 현재 출력과
일치한다고 이해한다. 새 다중색 전후 비교에서는 이 오해가 커진다.

**기존 보호장치 반증:** 출력에 Project를 사용하는 정책은 실제 파일의
값을 지키지만 후보 카드의 적용 상태 표시를 검증하지 않는다.
고정색 보존과 수동 역할 유지 역시 상태 라벨의 일치를 보장하지 않는다.

**최소 수정:** 후보 선택 표시의 뜻을 정한다. 후보 결과와 현재 채택 결과가
동일한 경우만 ‘적용됨’으로 표시하거나, 결과 편집 후 ‘이 후보에서 수정 중’
표시로 바꾼다. 미채택 후보와 현재 결과를 별도 제목으로 구분한다.
후보 재생성 후 예전 인덱스가 새 후보의 적용 상태가 되지 않게 한다.
색/위치/역할 변경과 개별·전체 되돌리기 모두 상태 판정에 포함한다.

**검증 기준:** 후보 적용 → 유연색 한 개 되돌리기 → 카드 적용 상태가
정확하게 변함 → 현재 결과/내보내기 값 일치. 새 후보 생성만 했을 때
미채택 후보가 적용됨으로 읽히지 않아야 한다. 키보드·스크린리더에도
동일한 상태가 전달되어야 한다.

## U3 — 다중 입력 오류를 잠깐의 공통 안내만으로 처리할 위험

우선순위: P2. 근거 확실성: 중간(기존 오류 처리를 계승할 경우).

**근거:** 명세 R16(39행)과 55–58행은 레이블·오류 안내·live region을
요구하지만 필드 연결과 오류 지속성을 정하지 않는다.
기존 `src/App.tsx:401–405`는 모든 notice를 5초 뒤 지운다.
`SwatchRow`의 210–215행은 잘못된 HEX를 공통 notice로 알리고
입력값을 직전 값으로 복원한다. 마지막 live region(1406행)은 오류 필드와
연결되어 있지 않다. 기존 E2E는 오류 안내가 순간 존재하는지만 확인한다.

**실패 조건 → 영향:** 12개의 입력색 중 한 행이나 좌표의 한 성분이
잘못되어 사용자가 다음 필드로 이동한다. 안내를 읽기 전에 사라지거나
값이 되돌아가면 어떤 입력이 반영되지 않았는지 찾기 어렵다.
스크린리더의 안내 큐가 길어질 때도 공통 성공 알림이 오류를 대체할 수 있다.

**기존 보호장치 반증:** `label`, `role=status`, `aria-live=polite`는 이름과
새 안내를 전달한다. 어떤 필드가 잘못되었고 아직 수정이 필요한지는
표현하지 않는다. 잘못된 값 차단은 작업 복구 안내와 별개다.

**최소 수정:** 잘못된 필드는 수정할 때까지 필드 옆에 오류를 유지하고
`aria-invalid`/`aria-describedby`로 연결한다. 제출 실패는 문제 행을
지목하고 첫 오류 필드로 이동할 수 있게 한다. 성공·저장 안내만 시간에
따라 닫고 조건 충돌은 해당 후보 또는 colormap 영역에 지속적으로 둔다.

**검증 기준:** 3번째 입력색의 잘못된 HEX와 좌표 범위 오류를 키보드로
제출 → 5초 이후에도 관련 행에 오류 존재 → 정상값 수정으로 오류 해소.
다른 성공 알림이 발생해도 미해결 오류가 남아야 한다. 모바일에서도
오류 행과 수정 제어가 보이고 문서 가로 overflow가 없어야 한다.

## 검토한 보호장치와 미검토

native details, range 대안, 명시적 레이블, 색 외 상태 표시, 760px 단일 열,
색/위치 잠금 분리, 원색 기준 보정과 명시적 후보 적용은 사용자 흐름에
적합한 설계다. 기존 reorder 버튼은 드래그에 의존하지 않는 대안이며
기본 focus-visible 스타일도 존재한다.

이번 리뷰는 소스·문서 읽기에 한정한다. 신규 구현, 실제 브라우저의 화면
크기·터치 목표·탭 순서, 색각 시뮬레이션, 생성 알고리즘, 출력 인코더,
schema 이행, 프로덕션 배포는 검토하지 않았다. 기존 E2E의 키보드 확인은
첫 헤더 링크 이동이고 새 편집/후보/되돌리기 흐름의 근거가 될 수 없다.

독립 1차 판정: U1의 상태 계약을 먼저 확정하고 U2/U3를 수용 기준에
포함하면 구현 가능한 사용자 흐름이다. 미구현 자체를 이유로 출시
불가능 판정을 내리지는 않았다.
