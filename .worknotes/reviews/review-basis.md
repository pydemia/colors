# Colors 색채 문서 검토 및 적용 방향

검토일: 2026-10-03 · 추가 검토: 2026-10-04  
기준: 사용자가 제공한 세 Google Docs, 현재 colors.pydemia.ai의 화면, 현재 작업공간의 구현. 아래 우선순위와 설계는 제안이다.

**권장 방향은 ‘의도를 색의 관계와 실제 사용 조건으로 바꾸는 팔레트 스튜디오’다.** 현재의 OKLCH·원본색 잠금·역할색·미리보기를 확장해, 사용자가 원하는 분위기를 만들고 그 색을 실제 제품에 적용할 수 있도록 한다. 다음 개선의 중심은 하나 이상의 사용자 선택색을 고정하거나 제한적으로 보정하는 추천, 생성 결과의 의도 반영, 명도·채도·면적 관계의 가시화, 역할별 검증, 내보내기다.

## 2. 현재 구현에서 확인한 출발점

기획서의 ‘기존 HSL/RGB 생성기에서 OKLCH로 전환’ 설명은 현재 상태와 다르다.

| 항목 | 현재 확인 | 다음 개선 |
| --- | --- | --- |
| 색 연산 | `src/lib/color.ts`가 culori의 OKLCH 변환과 chroma 감소를 사용한다 | 내부 정밀도와 색역 보정 이력을 보존한다 |
| 의도 입력 | 사용처, 분위기, 색 방향, 밝기, 채도, 피할 색을 입력한다 | 입력을 기준색 하나에서 후보 전체·역할색까지 전달한다 |
| 분위기 태그 | 첫 태그만 `conceptSeed()`의 색상 방향에 반영된다 | 주 분위기·보조 분위기의 역할을 명시하거나 실제로 함께 반영한다 |
| 사용처 | 생성 색에는 반영되지 않고 첫 미리보기 탭 선택에 쓰인다 | 사용처에 따라 명도 구조·역할·검증 조건을 다르게 적용한다 |
| 자유 메모 | 생성에 반영되지 않는다고 UI에 명시한다 | 우선 메모 용도로 유지한다. 문장 해석이 필요해지면 별도 기능으로 도입한다 |
| 피할 색 | 기준색의 색상각을 피하는 데만 쓰인다 | 파생색 포함 최종 후보를 검사하고, 회피 범위를 정한다 |
| 후보 스타일 | 은은한·선명한·깊은 세 후보를 만든다 | 분위기의 어두움과 화면의 Light/Dark 모드를 별도 입력으로 둔다 |
| 역할·잠금 | 5개 원본색과 사용처별 역할색이 분리되어 있다 | 사용자 선택, 자동 파생, 대비 보정의 출처와 재계산 정책을 명확히 한다 |
| 검증 | 일부 전경·배경 조합의 대비와 역할별 수정안을 제공한다 | 실제 미리보기에 등장하는 조합을 빠짐없이 검사한다 |
| 출력 | 프로젝트 JSON, 역할별 CSS 변수를 제공한다 | DTCG 토큰·Tailwind·검증한 프로그램 형식으로 확장한다 |

### 작은 재현으로 확인한 생성 한계

현재 `color.ts`를 직접 호출한 결과다. 전체 품질 평가나 모든 입력의 검증 결과는 아니다.

- 동일 입력에서 `moods: ['calm']`을 `['calm', 'bold']`로 바꿔도 기준색은 동일했다.
- 같은 콘셉트의 `useCases: ['web']`을 `['terminal']`로 바꿔도 기준색은 동일했다. 후보 생성 함수에도 사용처가 전달되지 않는다.
- 차분한 기본 콘셉트의 세 후보 배경 OKLCH L은 약 `0.975 / 0.936 / 0.820`이었다. ‘깊은’ 후보도 Dark 모드 배경을 의미하지 않는다.
- `#808080`의 단색 후보가 `#808080, #EEF9FC, #18323A, #8CBAC8, #77A4B2`로 나왔다. 무채색에서 정의되지 않은 hue를 대체하고 파생색에 chroma를 부여하기 때문이다. 무채색 유지 여부를 명시적인 선택으로 만들어야 한다.
- 코드상 `tetradic`은 두 accent에 `+90° / +180°`를 사용한다. 네 색상축을 의도한다면 `+270°` 축도 포함하거나 UI 이름을 구현에 맞게 조정해야 한다.

## 3. 먼저 바로잡을 개념과 사양

### 3.1. 명도, 상대 휘도, 영상 신호, 면적은 따로 다룬다

- **OKLCH L**: 색을 생성·조정할 때 사용하는 지각 명도 좌표.
- **상대 휘도 Y**: 출력 색을 선형화한 값으로 계산하는 WCAG 대비의 기반.
- **IRE**: 영상 신호의 레벨을 나타내는 단위. OKLCH L의 백분율로 치환하지 않는다.
- **60:30:10**: 화면에서 색이 차지하는 면적의 디자인 출발점. 색 개수나 휘도 비율이 아니다.

따라서 `Shadow L <= 0.25 : 60%`를 보편 공식으로 강제하지 않는다. 테마의 명도 범위와 사용 비율을 서로 다른 설정으로 둔다. 팔레트의 L 값 막대는 ‘명도 분포’라고 부르고, 이미지의 공간별 신호를 분석하지 않는 화면에는 ‘Waveform’ 이름을 붙이지 않는다. 색공간과 휘도의 구분은 [CSS Color 4의 색 용어](https://www.w3.org/TR/css-color-4/#color-terminology)를 기준으로 정리한다.

### 3.2. 미학적 원칙은 조절 가능한 휴리스틱으로 구현한다

`명도×0.6 + 채도×0.3 + 색상×0.1`은 문서에 검증 근거가 제시되지 않았다. 범위가 다른 좌표와 순환하는 hue를 그대로 더해 품질 점수로 사용하지 않는다. `ΔL < 0.25`, `C > 0.15`, 채도 40% 감소도 초기 실험값으로 취급한다.

‘따뜻한 빛이면 그림자는 반드시 차갑다’, ‘검정은 금지’, ‘고채도 네 개는 실패’ 같은 문구는 프리셋의 스타일 지침으로 바꾼다. 톤 비대칭과 미색 암부를 제안하되, 브랜드색·무채색·의도적인 강한 대비도 허용한다. 색상차는 원형 거리로 계산하고, 거의 무채색인 색의 hue 비교는 제외한다.

간상세포·원추세포의 수량 비율로 명도 민감도의 배수를 단정하는 설명과 괴테의 상승을 현대 광학의 계산 법칙으로 연결하는 설명은 제품 알고리즘의 근거에서 제외한다. 교육 자료로 공개할 때는 독립적인 원전·연구 확인이 필요하다.

### 3.3. Warm/Cool과 Tint부터 시작한다

1차 버전은 ‘따뜻하게 ↔ 차갑게’, ‘초록 기운 ↔ 자홍 기운’이라는 창작 조작으로 제공한다. 문서의 수식은 `a` 변화만 정의하므로 2축 변환 사양으로 불완전하다. Oklab의 `a, b` 두 좌표에 대한 변환, 명도별 적용 강도, 색역 처리와 잠금 예외를 정의해야 한다.

실제 Kelvin·CCT 조명 시뮬레이션을 표시하려면 광원 색도, 백색점, 색순응, 입력·출력 조건을 정의해야 한다. 따뜻한 색을 더하는 연산만으로 물리적 광원을 재현한다고 설명하지 않는다. 물리적 광혼합과 지각적 배색 편집의 연산 공간도 구분한다. [CSS Color 4](https://www.w3.org/TR/css-color-4/#color-terminology)는 광량의 가산 연산에 선형 광 공간이 필요함을 설명한다.

### 3.4. 대비 압축과 질감은 별도 기능이다

팔레트의 L 범위를 압축하면 색 사이의 명도 차이를 줄일 수 있다. 형태의 경계가 흐려지거나 필름 그레인·하이라이트 롤오프가 생기는 효과는 렌더링·이미지 변환 기능이다. ‘Soft’ 프리셋에 포함할 수 있지만 색 생성 규칙과 시각 효과를 별도 저장·제어한다. 저대비 분위기의 배경을 선택해도 UI 글자와 조작 요소에는 필요한 대비를 확보한다.

### 3.5. 접근성 보정은 역할과 사용 조건에 적용한다

일반 텍스트 `4.5:1`, 큰 텍스트 `3:1`을 구분하고, 조작 요소의 식별에 필요한 시각 정보와 의미 있는 그래픽에는 인접 색 대비 `3:1`을 검사한다. 큰 텍스트 여부는 실제 크기·굵기로 판단한다. [텍스트 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [비텍스트 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

현재 웹 대비 목록에는 `text/background`, `link/background`만 있다. 미리보기의 버튼은 `background`를 글자색, `primary`를 바탕색으로 사용하고, 작은 상단 문구에는 `secondary`가 사용된다. 이 조합들도 검증 목록과 역할에 연결해야 한다. `onPrimary`, `surface`, `textMuted`, 상태별 전경·배경과 `focusRing`을 우선 추가한다.

생성 단계에서는 기준색을 보존한 채 필요한 역할 파생색을 만든다. 사용자가 수정한 결과에는 경고와 전후 비교를 제공하고, 현재의 선택 적용 방식을 유지한다. 잠금·수동 수정 때문에 조건을 만족할 수 없으면 충돌을 표시한다. ‘검사한 역할 조합의 대비 통과’와 전체 WCAG 준수는 구분한다. 색각 차이 보기와 상태 라벨·아이콘·패턴도 함께 제공한다.

### 3.6. 레시피·내보내기·KPI의 근거를 보완한다

- 16개 레시피는 프리셋 원재료로 활용한다. 와다 산조 원전과의 대응·출처를 확인하기 전에는 ‘와다 산조의 검증된 16종’으로 단정하지 않는다. 문서의 HEX를 입력 기준으로 삼고 HSL/OKLCH 값은 다시 계산한다. 각 레시피의 3개 색에서 5개 원본색과 역할색을 만드는 정책을 정의한다.
- ‘W3C Design Tokens 표준’은 **DTCG Format Module 2025.10 호환**으로 고친다. 이 규격은 W3C Recommendation이 아닌 Community Group 규격이다. 일반 JSON 출력과 특정 Figma 플러그인에서 가져오기 확인한 출력도 구분한다. [DTCG 공식 규격](https://www.designtokens.org/tr/2025.10/format/).
- Tailwind 출력은 버전을 선택하게 한다. 문서의 JS config 예시와 현재의 CSS `@theme` 방식은 서로 다른 출력이다. [Tailwind 공식 색상 문서](https://tailwindcss.com/docs/colors).
- PRD의 익스포트율 4.2%, 세션 48초, 재방문율 8.1% 등은 측정 출처를 확인하지 못했다. 현재 저장소에서도 해당 계측 코드를 찾지 못했지만 외부 계측의 존재까지 배제할 수는 없다. 기준치는 ‘미측정/출처 확인 필요’로 두고, 목표치는 가설로 표기한다.

## 4. 권장 제품 흐름과 기능

**사용처·화면 모드 선택 → 분위기/레시피 또는 기준색 선택 → 후보 3개 비교 → 역할·명도·비율 조정 → 검증 → 적용 파일 받기**

기존 사용처인 웹·발행물·PowerPoint·편집기·터미널을 유지한다. 영상·실내·패션은 후속 확장으로 다룬다. 초보·전문가용 엔진을 따로 만들지 않고 같은 프로젝트에 기본 조작과 접힌 상세 조작을 둔다.

### A. 의도가 실제 후보에 반영되는 생성

- ‘차분한’은 주변과 보조색의 chroma를 낮추고 강조색 수·비중을 제한한다.
- ‘대담한’은 강조 역할의 대비·chroma·비중을 높이는 방향으로 해석한다.
- 주 분위기를 먼저 고르고 보조 분위기는 한두 개까지 추가한다. 함께 구현하지 않는 태그는 생성 입력으로 제시하지 않는다.
- 피할 색의 의미를 ‘이 색상 계열 회피’와 ‘이 색 근처 회피’로 구분할 수 있다. 최종 원본·역할색을 검사하고 상태색 등 예외를 표시한다.
- 모든 입력과 버전, 재생성 순서를 저장해 같은 결과를 재현한다. 새 후보에서도 원래 조건을 적용한다.

### B. 설명을 가진 레시피 라이브러리

16종을 구조화하고, 검증이 끝난 대표 레시피 6종을 첫 화면에 추천한다. 카드는 이름·색 조합·사용 비율·권장 사용처·짧은 선택 이유를 가진다. 예를 들어 ‘냉정한 신뢰 + 작은 온기’는 블루 중심과 살구색 보조 조합으로 보여 줄 수 있다. 영화명이나 서사적 비유는 탐색을 돕는 설명으로 쓴다.

각 레시피는 `id`, `version`, 원본 색·출처, 분위기 태그, 권장 화면 모드, 명도 구조, 강조 비중, 조정 범위를 갖는다. 전역 재생성으로 레시피의 정체성이 사라지지 않도록 변형 범위를 제한한다.

### C. 명도·채도·면적을 보는 편집

- OKLCH L/C/H 상세 편집과 색역 경고.
- 같은 색을 밝은·어두운·유색 배경에 나란히 놓은 맥락 비교.
- 중립 명도 보기. OKLCH L 구조와 WCAG 상대 휘도 검사는 구분해 표시한다.
- 주조·보조·강조의 사용 비율을 바꾸는 포스터/카드 미리보기. `60:30:10`은 선택 가능한 초기값으로 둔다.
- ‘강조색 유지, 주변 채도 낮추기’ 조작. 원본 잠금과 사용자 역할 수정은 보존한다.
- Light/Dark 전환. 각각에 맞는 역할 파생색을 만들고 한 화면에서 비교한다.

### D. 적용 조건을 드러내는 미리보기

먼저 웹 카드·버튼·입력·상태 메시지와 PowerPoint/발행물의 본문·표·차트를 추가한다. 그다음 편집기의 모든 구문색과 터미널 ANSI 전경을 실제 배경 및 선택 영역 위에 배치한다. 색만 나열하는 견본보다 읽기·강조·구분 문제를 확인할 수 있는 화면을 우선한다.

후보 카드에는 ‘본문 대비’, ‘강조색 비중’, ‘명도 범위’, ‘잠금으로 해결되지 않은 항목’을 짧게 보여 준다. 예술적 선호를 단일 숫자로 평가하지 않고, 객관적 제약과 선택 이유를 구분한다.

### E. 실제로 가져다 쓸 수 있는 출력

CSS에 Light/Dark 역할을 포함하고, DTCG JSON·Tailwind 출력은 소비 도구에서 읽어 확인한다. 이후 기존 제품 범위의 VS Code·Windows Terminal 등 실제 가져오기 가능한 형식을 순차 제공한다. 지원 완료 표시는 대상 프로그램 검증을 통과한 형식에 붙인다.

`.ase`, Display-P3, 사진 기반 분석은 이 기반이 정리된 뒤 확장한다. 인쇄에는 ICC 프로파일·출력 조건이 필요하고, PCCS 톤 이름이나 HEX만으로 재질·인쇄 결과를 보장할 수 없다. [Adobe의 인쇄 색상 관리 안내](https://helpx.adobe.com/photoshop/using/color-managing-documents--printing.html)를 참고한다.

3D LUT는 팔레트 몇 개만으로 유일하게 정해지지 않는다. 입력 RGB 전체를 출력 RGB로 보내는 변환과 색공간·전달함수 조건이 필요하다. 영화 프레임·LUT·3D 룸 기능은 별도 영상/렌더링 프로젝트로 검증한 뒤 제품에 연결한다.

## 5. 현재 코드에 적용하는 설계

### 데이터와 편집의 중요한 경계

- 화면의 5개 원본색과 여러 역할 파생색을 분리하는 기존 구조를 유지한다. 실제 사용 비율은 별도 정보로 저장한다.
- 고정한 HEX는 정확히 보존한다. 생성·조정용 OKLCH 값은 정밀도를 유지하고 출력 시 색역과 직렬화를 처리한다. 반복 HEX 왕복으로 원래 의도가 소실되지 않게 한다. [CSS Color 4](https://www.w3.org/TR/css-color-4/)의 색 변환·색역 매핑 개념을 참고한다.
- 역할의 ‘사용자 연결’과 ‘자동 연결’을 구분한다. 현재 `setRoleSwatch()`는 사용자 연결도 `reason: null`로 저장하고 `chooseCandidate()`는 이를 자동 역할로 덮을 수 있으므로, 새 후보에서도 수동 선택을 보존하는 정책이 필요하다.
- 현재 자동 파생색은 HEX 스냅샷이다. 원본색 편집에 따라 재계산하려면 파생 규칙과 의존 관계를 저장해야 한다. 새 규칙에서는 자동 파생은 갱신하고, 수동 수정과 채택한 대비 수정은 보존하는 정책을 명시한다.
- 하나의 전경이 여러 배경 위에 쓰이면 모든 조합을 함께 검사한다. 한 조합의 보정이 다른 조합을 깨뜨릴 때는 역할 분리 또는 배경 수정안을 제시한다.
- 프로젝트 백업 JSON과 교환용 디자인 토큰 JSON은 다른 형식이다. 각각 버전·복원/소비 검증을 갖춘다.

## 7. 성공 지표 제안

주 지표는 **생성한 색을 실제로 가져다 쓰는 비율**이다. 세션별 `후보 생성 → 선택 → 역할 조정/미리보기 → 검증 → 내보내기` 흐름을 계측한다. 내보내기율의 분모는 ‘팔레트를 생성한 세션’, 분자는 ‘사용 가능한 출력을 한 번 이상 받은 세션’처럼 명시한다. 프로젝트 백업과 적용용 출력을 나눠 측정한다.

보조 지표는 첫 사용 가능한 출력까지 걸린 시간, 레시피별 채택률, 검사한 역할 조합의 대비 통과율, 잠금으로 해결되지 않은 조건의 빈도, 수정안 채택/되돌리기, 저장 프로젝트 재사용이다. 체류 시간 증가는 사용 난이도가 커진 결과일 수도 있으므로 단독 목표로 삼지 않는다. D30 재방문은 사용자 식별·측정 방식이 정해진 뒤 평가한다.

다음 릴리스의 권장 범위는 **여러 사용자색의 고정/제한 보정 추천 + 생성 규칙 정비 + 대표 레시피 + Light/Dark 역할 + 명도/비율 미리보기 + 검증 범위 확대**다. 연속 colormap은 같은 추천 입력을 사용하되 용도별 명도 흐름과 위치 정보를 검증하는 별도 출력으로 확장한다. 이 범위를 통해 세 문서의 중심인 명도 위계·맥락·의도를 현재 제품에서 직접 체험할 수 있다.

## 8. 색상환·표색계·가색/감색 선택 확장

사용자의 2026-10-04 질문을 반영한 설계 제안이다. 세 선택은 역할이 다르므로 독립 설정으로 둔다. 구현 범위는 좌표 변환·색상환부터 넓히고, 기준 색표와 혼합 모델을 단계적으로 연결한다.

| 선택 | 사용자에게 제공할 후보 | 선택의 효과 |
| --- | --- | --- |
| 색상환 / 배색 기준 | 지각형 OKLCH, RGB 기반 HSL/HSV, 회화형 RYB 근사, 후속 먼셀/PCCS 색상환 | 유사색·보색·삼각·사각 배색을 고르는 색상 위치와 관계 |
| 색 표시·편집 좌표 | HEX/sRGB, HSL/HSV, OKLab/OKLCH, CIELAB/LCH; 프로파일 준비 후 CMYK | 같은 색의 입력값·편집 축·복사 형식 |
| 표색계 / 색표 탐색 | 먼셀 H V/C, PCCS 색상·톤, 후속 NCS | 기준 색표의 표기와 구조로 색을 탐색·선택하거나 가까운 색을 찾기 |
| 혼합 모델 | 지각 보간, 빛의 가색, 필터 감색 근사, 안료 혼합 근사 | 두 색의 중간색·혼합 경로와 혼합으로 파생하는 색 |

### 8.1. 색상환은 배색 관계를 결정한다

현재 조화 유형은 유지하고, 색상환 선택을 추가한다. 선택한 체계에서 hue 위치를 계산하고 조화 규칙을 적용한 뒤 원래 색 표현으로 돌려보낸다. 명도·채도 조정과 역할 대비 검사는 뒤에서 수행한다. 색상환마다 hue 좌표가 다르므로 동일한 수치 각도를 서로 복사하지 않는다.

RYB는 회화의 배색 관계를 탐색하는 근사 색상환으로 정의하고 매핑·버전을 저장한다. 사용자가 RYB 색상환을 골라도 안료 혼합 모델은 별도로 선택한다. ‘보색’은 색상환에서 마주보는 색과 혼합 후 중성화되는 색의 의미를 구분해 표시한다.

색상환을 바꾸면 새 후보를 보여 준다. 기존 팔레트에 적용하는 동작과 화면에 색상환만 바꿔 보는 동작을 구분하고, 잠금색·수동 역할값을 보존한다. 고정 L/C의 색상환에서 표시 색역을 벗어나는 부분도 표시한다.

### 8.2. 표색계는 좌표 표현과 기준 색표를 함께 지원한다

첫 단계는 같은 색을 HEX/RGB·HSL/HSV·OKLCH·Lab/LCH로 보고 편집하는 기능이다. 표시 체계만 전환할 때는 정밀한 원본 색과 출력 색역을 유지한다. HEX는 sRGB의 직렬화 형식이며 독립된 색공간으로 취급하지 않는다. RGB에는 sRGB/Display-P3 등 공간 이름을, Lab에는 백색점 등 변환 조건을 명시한다. [CSS Color 4](https://www.w3.org/TR/css-color-4/#color-terminology).

먼셀·PCCS·NCS는 각각의 표기와 기준 색표를 가진 체계로 제공한다. 먼셀은 색상·명도·채도로 표기하며, PCCS의 Hue-Tone 구조는 분위기·톤 선택에 연결할 수 있다. NCS는 흑색량·유채색량·색상 등의 속성으로 탐색한다. [먼셀 설명](https://munsell.com/wp-content/uploads/2011/03/munsell-color-system-cleland.pdf), [일본색채연구소 PCCS 설명](https://www.jcri.jp/achievement_1), [NCS 공식 설명](https://ncscolour.com/en-eu/pages/the-system).

기준 색표의 측색 데이터·관찰 조건·이용 조건을 확인해 연결한다. 정확한 표기 대응과 ‘가까운 색표 샘플’ 검색을 구분하고, 근사 결과에는 색차와 근사 표시를 붙인다. PCCS의 대표 색 블록을 임의 연속 좌표로 간주하지 않는다. [PCCS 개정 논의](https://www.jcri.jp/square/journal/pccs_revision).

### 8.3. 가색·감색·지각 보간의 결과를 비교한다

- **지각 보간**: OKLab/OKLCH 등 선택한 공간에서 중간색을 만든다. OKLCH에서는 hue 경로도 선택할 수 있다. 그라데이션과 팔레트 변형에 사용한다.
- **가색 — 빛**: 선형 sRGB 또는 XYZ에서 계산한다. 빛의 세기 합산과 혼합 비율의 가중 평균을 별도 조작으로 구분한다. 감마 인코딩된 RGB 숫자를 바로 평균내지 않는다. 출력 범위를 넘는 밝기는 노출·매핑 조건을 명시한다. [CSS Color 4의 선형 광 설명](https://www.w3.org/TR/css-color-4/#color-terminology).
- **감색 — 필터 근사**: 투과율/광학 농도 기반의 선택한 근사 모델을 사용한다. 광원·필터의 스펙트럼이 없는 RGB 입력의 한계를 표시한다.
- **감색 — 안료 근사**: 흡수·산란을 다루는 모델을 사용한다. Kubelka–Munk 기반 Mixbox 같은 접근을 후보로 검토할 수 있다. RGB 입력에서 추정한 안료 혼합 결과와 특정 실제 물감의 혼합 예측은 구분한다. [Mixbox 개발자의 모델 설명](https://scrtwpns.com/mixbox/).
- **CMYK 인쇄**: 출력 조건·ICC 프로파일이 정해진 색 분해·미리보기로 제공한다. 임의 CMYK 퍼센트 평균을 실제 잉크 혼합 모델로 사용하지 않는다. 인쇄 조건에 따라 CMYK 색역이 달라진다. [Adobe 색 모드 설명](https://helpx.adobe.com/photoshop/using/color-modes.html).

UI에는 두 입력색, 0–100% 혼합 비율, 모델별 결과와 그라데이션, 팔레트에 추가/역할에 적용하는 동작을 둔다. 각 결과에 계산 모델과 출력 색역을 기록한다. 화면에는 RGB로 표시하되 감색 계산의 의미와 출처를 보존한다.

### 8.4. 기본값과 저장·검증

웹 용도의 권장 기본값은 ‘OKLCH 색상환 + OKLCH 편집/HEX 복사 + 지각 보간 + sRGB 출력’이다. 회화 탐색에는 ‘RYB 근사 또는 PCCS 탐색 + 안료 근사’를 추천할 수 있다. 사용처 프리셋은 이 설정들을 채우며, 상세 설정에서 각각 변경할 수 있게 한다.

프로젝트에는 `wheelModel`, `editingSpace`, `referenceSystem`, `mixingModel`, `outputColorSpace`, 모델·색표 버전, 필요한 프로파일/관찰 조건, 혼합 비율과 입력색을 저장한다. 조화 생성·혼합·색역 처리·최종 역할 검증을 각각 분리해 동일 설정의 결과를 재현한다.

완료 조건은 좌표 표시 전환에서 색 보존, 무채색의 hue 처리, 색상환별 배색 결과 비교, 혼합 비율의 끝점·경로 확인, 가색 합산/평균의 구분, 근사 표시, 색역 경고, 프로젝트 저장·재개에서 설정과 결과 보존이다.

## 9. 하나 이상의 사용자색으로 추천: 고정색과 보정 가능한 초안색

사용자의 2026-10-04 추가 요구를 반영한 핵심 기능이다. 사용자는 하나 이상의 색을 입력하고, 색마다 ‘색 고정’ checkbox를 선택한다. 켜진 색은 정확히 유지하고, 꺼진 색도 조합 의도를 파악하는 기준으로 사용하면서 허용 범위 안에서 보정한다. 출력은 웹/테마용 팔레트와 데이터/그라데이션용 연속 colormap을 지원하는 방향으로 설계한다.

### 9.1. 사용자 입력과 추천 동작

| 입력 | 권장 동작 |
| --- | --- |
| 사용자색 1개 | 색을 기준으로 주변색·명도 구조·역할 또는 colormap 경로를 추천한다 |
| 사용자색 여러 개 | 각 색의 개별 특성과 색 사이의 명도차·채도차·색상 관계를 함께 사용한다 |
| 색 고정 ON | 후보 생성·재생성·보정에서 원래 색값을 정확히 보존한다 |
| 색 고정 OFF | 원래 색을 참고하면서 허용 보정량 이내에서 L/C/H를 조정한다 |
| ON/OFF 혼합 | 고정색을 제약으로 삼고, 초안색과 추가 생성색으로 나머지 구조를 맞춘다 |
| 보정량 0 | OFF인 색도 색값을 유지한다. 색 위치·추가색 추천은 별도 조건에 따른다 |

색 고정은 기본 ON을 권장한다. ‘전체 색 고정/해제’와 색별 checkbox를 함께 제공하고, 전체 보정량은 ‘변경 없음 / 미세 조정 / 조정’ 또는 슬라이더로 표시한다. 조정 모드도 사용자가 정한 변경 범위를 지킨다. 고정 해제가 추천에서 해당 색을 제외하는 동작이 되지 않도록 한다.

각 입력색에 자동/배경/주색/강조 등 역할 의도를 선택적으로 붙일 수 있다. 입력 개수와 출력 개수는 별도다. 모든 사용자색을 결과의 대응 색으로 유지하는 기본 정책을 두고, 출력 색 수가 이를 수용하지 못하면 색 수 변경안을 보여 준다. 입력을 조용히 버리거나 첫 색 하나로 축약하지 않는다.

### 9.2. 선택색에서 조합 의도를 추정하고 확인한다

먼저 명도 분포, 채도 분포, 원형 색상차, 따뜻함/차가움의 관계, 입력 순서와 역할 정보를 분석한다. 여러 색을 단순 평균한 대표색 하나로 축약하지 않는다. 보색처럼 평균에서 정보가 소실되기 쉬운 관계도 유지한다.

‘따뜻한 강조색과 차가운 바탕’, ‘낮은 채도의 차분한 조합’, ‘두 색의 대립을 살리는 조합’처럼 추정한 의도를 짧게 보여 준다. 사용자가 확인하거나 분위기·조화 유형·용도를 바꿀 수 있게 한다. 관계 추정만으로 사용자의 감정·목적을 확정하지 않는다. 1차 구현은 결정적인 규칙으로 가능하고, 자연어 의도 해석은 후속 기능으로 연결할 수 있다.

선택한 색상환은 배색 관계 분석에, 선택한 표색계는 표시·편집에, 선택한 혼합 모델은 중간색과 경로 생성에 사용한다. 기존의 조화 유형·Light/Dark·사용처·피할 색도 함께 전달한다.

### 9.3. 고정과 보정의 알고리즘 계약

각 입력색 `i`의 원본을 `originalColor[i]`, 후보에서 대응하는 색을 `resolvedColor[i]`로 저장한다.

- 고정 ON이면 `resolvedColor[i] = originalColor[i]`를 제약으로 둔다. 원본 색역·정밀도를 보존하고, 출력 색역이 표현하지 못하면 충돌을 표시한다.
- 고정 OFF이면 원본 대비 지각 색차와 L/C/H 변경을 제한한다. 지각 색차는 ΔEOK 등을 사용하고 실제 허용값은 사례 평가로 정한다. 색상각의 순환과 거의 무채색인 색의 hue를 별도로 처리한다. [CSS Color 4의 색차 정의](https://www.w3.org/TR/css-color-4/#color-difference-OK).
- 모든 보정량은 처음 입력한 원본 기준으로 계산한다. 반복 추천에서 조금씩 누적되어 전혀 다른 색으로 이동하지 않게 한다.
- 사용자색의 hue를 우선 보존하고 명도·채도부터 조정하는 기본 정책을 둔다. hue 조정 허용 여부와 개별 보정 범위는 상세 설정으로 제공한다.
- 고정색·위치·보정 제한은 후보를 만든 뒤 덮어쓰는 방식으로 처리하지 않고 처음부터 생성·평가 조건에 넣는다.
- 후보의 추가 생성색은 사용자색에서 파생하거나 배색 관계를 보완한다. 입력색과 추가색의 출처를 구분한다.

품질 평가는 고정 보존·허용 변경량·출력 색역 등 필수 조건을 먼저 확인하고, 그 안에서 원본 충실도·의도 유지·용도별 가독성/구분성·경로의 매끄러움으로 비교한다. ‘완성도’를 단일 보편 점수로 표시하지 않고 개선 이유와 해결하지 못한 조건을 제시한다.

### 9.4. 팔레트와 연속 colormap에 맞는 추천

웹/테마용 팔레트는 사용처별 역할, 전경·배경 대비, 강조 비중을 평가한다. 데이터용 colormap은 범주형·순차형·발산형·순환형을 고르게 한다. 순차형은 명도 흐름, 발산형은 기준점 양쪽의 흐름, 순환형은 양 끝의 연결, 범주형은 색 사이 구분을 평가한다. 유형 선택은 데이터의 의미를 기준으로 한다. [Matplotlib의 colormap 선택 안내](https://matplotlib.org/stable/users/explain/colors/colormaps.html).

연속 colormap에서는 사용자색을 기준점(anchor/stop)으로 사용한다. 자동 위치와 직접 지정한 0–1 위치를 제공하며 ‘색 고정’과 ‘위치 고정’을 구분한다. 색값을 고정하더라도 위치 고정이 없으면 의도와 명도 흐름에 맞춘 배치를 제안할 수 있다. 순서 변경안은 전후 비교에서 명시한다.

고정색이 지정 위치에 정확히 나타나도록 경로를 구성한다. 조화·혼합·보간·색역 매핑 뒤 최종 출력에서 이를 다시 확인한다. 지각 보간과 빛/안료 혼합의 경로가 달라지면 각각의 결과를 평가한다. 모든 모델에 동일한 지각 균등성을 보장하지 않는다.

CSS stop 정의와 정해진 개수의 샘플 색 목록은 구분한다. 예를 들어 기준점이 `t=0.3`이면 균일한 256개 샘플에 그 위치가 정확히 포함되지 않을 수 있다. 샘플 출력에서도 고정색을 반드시 포함해야 하면 기준점을 샘플 위치에 맞추거나 해당 색을 포함하는 샘플 정책을 명시한다. 내보내기 때문에 고정색이 사라지거나 변경되는 결과를 성공으로 표시하지 않는다.

### 9.5. 후보 비교 UI

추천은 ‘원본 유지 중심 / 명도 구조 정리 / 강조 관계 정리’ 등 세 방향으로 보여 주되, 모두 동일한 고정·보정 조건을 준수한다. 각 후보에는 다음을 표시한다.

- 원본색과 추천색을 나란히 표시하고 입력색 ID로 대응 관계를 유지한다.
- 고정 여부, 변경된 L/C/H·색차, 보정 이유와 추가 생성색을 표시한다.
- 팔레트는 역할 미리보기, 연속 colormap은 색 띠·명도 흐름·히트맵 예시를 보여 준다.
- ‘이 색만 원본으로’, ‘변경 전체 되돌리기’, ‘이 후보 적용’을 제공한다. 일부 색만 되돌리면 결과 전체를 다시 검사한다.

사용자가 checkbox를 바꿨을 때는 추천을 갱신하거나 재추천이 필요한 상태를 명시한다. 현재 적용한 결과를 자동으로 덮어쓰지 않는다. 후보를 채택해도 원본 사용자색은 보존한다.

### 9.6. 조건 충돌과 데이터 확장

지정 위치의 고정색 때문에 순차형 명도 흐름이 역전되거나, 순환형의 고정된 양 끝이 서로 다르거나, 모든 색 고정으로 역할 대비를 확보할 수 없는 경우가 있다. 이유를 표시하고 ‘위치 자동 배치’, ‘한 색의 고정 해제’, ‘역할용 파생색 추가’, ‘유형 변경’ 등 가능한 해결안을 제시한다. 고정색 변경과 허용 보정량 확대는 사용자가 선택한 뒤에만 수행한다.

현재 `generateCandidates(seedInput, harmony, generation)`는 기준색 한 개를 받고, `chooseCandidate()`가 나중에 잠긴 색을 유지한다. 다중 입력색의 관계를 고려하도록 생성 인터페이스를 확장해야 한다. 원본 팔레트 5개 고정 계약도 입력색 배열·출력 개수·연속 경로를 수용하도록 마이그레이션한다.

저장 데이터에는 입력색 ID·원본값·고정 여부·허용 보정량·역할·위치와 위치 고정 여부, 추정/확인된 의도, 결과와 입력의 대응, colormap 유형·샘플 정책·생성 버전을 포함한다. 사용자 선택색 원본과 채택한 추천 결과를 구분한다.

완료 조건은 단일/다중 입력, 전체/부분 고정, 허용 범위 보정, 반복 추천의 원본 기준 유지, 후보 적용·되돌리기, 순서/위치 보존, 색역 처리 후 고정값 보존, 유형별 품질·조건 충돌 표시, 저장·내보내기 왕복에서 원본과 대응 관계 보존이다.
