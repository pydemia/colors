## I-U1 — ‘새 후보 만들기’가 현재 결과도 즉시 교체한다

우선순위 P1 · 근거 확실성 높음 · 관련 R02/R03/R15.

**위치:** `App.tsx:493–507`의 `regenerateCandidates()` 및
`1021–1023`의 버튼, `project.ts:372–388`의 `regenerate()`.
검토 문서 284–286행은 추천 갱신과 현재 적용 결과를 구분한다.

**실패 조건 → 영향:** 고정색과 유연색을 입력해 생성하고 두 번째 또는
세 번째 후보를 채택한다. 이어 ‘새 후보 만들기’를 누르면
`regenerate()`가 `chooseCandidate(..., candidates[0])`를 호출하므로
새 후보를 선택하기 전에 기존 결과가 첫 후보로 바뀐다. `setProject()`와
`setSelectedCandidate(0)`가 이를 바로 채택하고 자동 저장한다.
사용자는 현재 후보를 기준으로 새 제안을 비교할 수 없으며 유연색과
자동 파생 역할이 생성 동작만으로 교체된다.

**보호장치 반증:** `RefinementPanel`의 ‘설정으로 새 추천 적용’은 명시적인
채택 문구이므로 즉시 첫 후보 적용이 이해 가능하다. 하지만 일반 버튼은
‘새 후보 만들기’라고만 말하며 알림도 ‘만들었습니다’다. 잠금·수동 역할
보존은 유연색과 자동 역할의 채택 상태를 보호하지 않는다. 기존 E2E의
재생성 검사는 고정색 한 개만 검사해서 이 실패를 잡지 못한다.

**최소 수정:** 일반 재추천은 새 후보와 생성 번호만 갱신하고 채택 결과,
역할·출력을 유지한다. 새 후보 중 하나를 누를 때 교체한다. 변경 뒤
후보 배열이 비워져도 재추천 버튼에 접근할 수 있도록 후보 영역 밖에 둔다.
설정 적용과 일반 재추천의 문구·채택 정책을 서로 명확히 구분한다.

**수용 기준:** 후보 2의 유연색/자동 역할/JSON을 기록 → 새 후보 생성 →
그 값 유지 및 새 후보 3개 표시 → 새 후보 채택 후에만 값과 출력 변경.
생성만으로 후보 1이 `aria-pressed=true`가 되면 안 된다.

## I-U2 — 현재 팔레트의 회피 조건 대신 재생성된 후보들의 경고를 표시한다

우선순위 P1 · 근거 확실성 높음 · 관련 R03/R11.

**위치:** `StudioPanels.tsx:183–186`, `249–250`;
`project.ts:414–434`의 직접 편집;
`studio.ts:271–285`의 추천 경고 생성.
검토 문서 140행은 편집·잠금·수동 값이 적용된 실제 결과를 다시 검사하도록 한다.

**실패 조건 → 영향:** 콘셉트에서 피할 색 `#FF0000`을 지정하고 생성한다.
이 경로는 `studio.anchors=[]`다. 생성색 하나의 HEX를 `#FF0000`으로 직접
편집하면 `setSwatchHex()`는 swatch만 바꾸고 존재하지 않는 anchor를 추가하지
않는다. 분석은 현재 `project.swatches`의 회피 조건을 검사하지 않고
`recommend(studio)`의 새 후보들만 검사한다. 따라서 실제 팔레트가 피할
색을 포함해도 회피 충돌이 표시되지 않는다. 반대로 특정 미채택 후보의
경고가 현재 결과의 경고로 함께 보일 수도 있다.

**보호장치 반증:** `validateMap(stops, s)`는 위치·명도 흐름을 검사하고
실제 swatch를 입력받으므로 해당 범위는 보호된다. 그러나 회피 조건을
검사하지 않는다. 통과 문구가 ‘위치·명도 조건’으로 좁혀져 있는 점은
전체 적합성 오인을 줄이지만 R03의 현재 팔레트 회피 검사를 대신하지 않는다.
기존 단위 테스트는 `recommend()`의 고정색 회피 경고를 확인하며,
직접 편집 후의 현재 결과 경고를 확인하지 않는다.

**최소 수정:** 현재 결과 검사를 `project.swatches`에 적용한다. 회피 조건,
원색 기준 보정 한계, 고정값을 현재 결과에서 검사한 안내와 미채택 후보별
경고를 구분한다. 후보 경고는 해당 후보 또는 생성 결과 요약에서 표시하고,
현재 충돌은 접힌 분석 내부에만 숨기지 않는다. 사용자 직접 편집을 막기보다
해당 색 ID와 충돌 이유를 알려 주면 된다.

**수용 기준:** 위 재현에서 현재 색 ID와 `#FF0000` 회피 충돌이 지속 표시되고
다른 색으로 수정하면 해소된다. 미채택 후보에서만 발생한 경고가 현재 결과의
경고로 표시되지 않아야 한다. 편집 뒤 CSS/JSON의 색과 검사 대상이 같아야 한다.

## I-U3 — 추천색을 다시 잠갔을 때 원색 보존 안내가 사실과 다르다

우선순위 P2 · 근거 확실성 높음 · 관련 R01/R02/R16.

**위치:** `project.ts:399–402`, `studio.ts:102–103`,
`StudioPanels.tsx:143–166`, `App.tsx:1080–1094`.

**실패 조건 → 영향:** 유연색의 추천색이 `originalHex`와 다른 후보를 채택한
뒤 현재 swatch를 잠근다. 데이터 계약은 `fixedHex=현재 추천색`을 보존하고
`originalHex`를 계속 보정 기준으로 남긴다. 그러나 비교 UI는 변경 전 원색과
다른 결과를 나란히 보여 주면서 ‘고정한 원색을 보존’이라고 설명하고,
잠긴 색이면 실제 원색 대비 ΔEOK도 숨긴다. 사용자는 자신의 최초 색을
보존한 것으로 이해할 수 있다.

**보호장치 반증:** `fixedHex`를 보존하는 계산 자체는 일관되며 잠금 해제 후
원색 기준 보정도 유지한다. 두 색 칩과 HEX는 차이를 보여 준다. 다만 별도
고정 목표값 없이 ‘원색 보존’으로 이름 붙인 상태·이유는 계산과 다르다.

**최소 수정:** 처음부터 고정한 입력색과 현재 추천색을 고정한 경우를 구분한다.
`fixedHex ?? originalHex`를 고정 목표로 표시하고 후자는 ‘현재 색 고정’이라고
설명한다. 최초 입력색은 초안 기준으로 별도 유지하고, 다르면 원색 대비
색차를 계속 보여 준다. 원색 복원과 현재 결과 잠금의 의미를 동일시하지 않는다.

**수용 기준:** 원색과 다른 유연색 채택 → 잠금 ON → 고정 목표 HEX가
화면/출력/재추천에서 동일하며 ‘최초 원색 그대로’라는 안내를 하지 않음.
잠금 OFF 후 되돌리기는 최초 원색으로 돌아가야 한다.

## I-U4 — 색별 되돌리기·위치 제어의 접근 가능한 이름에 대상 색이 없다

우선순위 P2 · 근거 확실성 높음 · 관련 R12/R16.

**위치:** `StudioPanels.tsx:167`, `243–247`.

**실패 조건 → 영향:** 입력색이 여러 개일 때 키보드 Tab이나 스크린리더의
폼 제어/버튼 목록으로 이동하면 모든 개별 버튼이 ‘이 색 되돌리기’, 모든
숫자 입력이 ‘위치 t’, 모든 체크박스가 ‘위치 고정’으로 전달된다.
옆의 ID/HEX는 `<code>`일 뿐 제어의 이름·설명 또는 그룹 레이블과 연결되지
않는다. 사용자가 어느 색을 복원하거나 어느 stop을 움직이는지 확인하려면
제어에서 빠져나와 주변 텍스트를 다시 읽어야 한다.

**보호장치 반증:** 각 제어에는 일반 레이블이 있고 화면에서 ID/HEX도 보인다.
따라서 이름 없는 컨트롤은 아니다. 그러나 2~12개의 동일한 이름 중
대상을 구별하는 정보가 빠져 있다. 기존 E2E는 `.nth()`로 대상을 선택하고,
키보드 테스트는 헤더 링크 Tab 이동만 확인하므로 이 실패를 검증하지 않는다.

**최소 수정:** 개별 복원 버튼에 색 ID/순번을 포함한 이름을 붙인다.
stop별 fieldset/legend 또는 고유 `aria-labelledby`로 ID/HEX와 연결하고,
위치 입력 및 위치 고정에 대상 색과 단위를 전달한다. 복원 뒤 상태 안내에도
대상 ID를 포함한다.

**수용 기준:** 3색에서 각 버튼·t 입력·위치 고정의 접근 가능한 이름이
서로 구별된다. 키보드로 두 번째 색만 복원·이동했을 때 실제 두 번째 색이
바뀌고 안내에도 그 ID가 포함된다.

## I-U5 — focusRing 역할은 계산되지만 미리보기에서 볼 수 없다

우선순위 P2 · 근거 확실성 높음 · 관련 R10/R11.

**위치:** `UsagePreview.tsx:26`, `37`, `52`;
`styles.css` 전체의 `--preview-focus` 사용 검색;
`project.ts:248`, `284`.

**실패 조건 → 영향:** 사용자가 focusRing 역할을 수정하면 대비 목록의
색·비율은 바뀐다. 웹 시안은 CSS 변수 `--preview-focus`를 전달하지만 이
변수를 사용하는 CSS가 없고 시안의 버튼은 focus 불가능한 `<span>`이다.
따라서 포커스 표시가 주색/표면/바탕에서 실제로 어떻게 보이는지 확인할
수 없다. 역할 편집의 미리보기 피드백이 이 역할에만 끊긴다.

**보호장치 반증:** 앱 자체의 global `:focus-visible` 테두리는 키보드 조작을
돕고, 대비 검사도 focusRing/background의 3:1 값을 정확히 대상으로 삼는다.
하지만 앱의 고정 테두리 색은 사용자 프로젝트의 focusRing 미리보기가 아니다.

**최소 수정:** 웹 시안에 초점 가능한 실제 버튼 또는 명시적인 포커스 상태
샘플을 두고 프로젝트의 focusRing을 테두리로 사용한다. 실제 인접 배경과
검사 목록의 배경이 일치하게 한다. 사용자가 키보드로 상태를 확인할 수
있게 하되 모사 버튼에 가짜 제출 동작을 추가할 필요는 없다.

**수용 기준:** focusRing HEX 변경 → 시안의 테두리 실제 색 변경 →
키보드 포커스 시 같은 표시 확인. 시안에서 테두리가 만나는 배경과
대비 검사 대상이 동일해야 한다.

## 보호장치 확인과 미검토

설정 초안의 명시적 적용, 결과 편집 후 후보 선택 해제, 지속 안내와 닫기,
native details/range, 입력색 `aria-invalid`, 고정색 입력 비활성화,
키보드 reorder 버튼, 상태 아이콘+글자, 모바일의 minmax(0,1fr) 전환은
코드에 존재한다. 앞선 설계 리뷰 U2의 기본 후보 상태 문제와 U3의
5초 뒤 안내 삭제 문제는 수정된 것으로 확인했다.

최대 12 입력의 전체 고정/부분 고정, 개별 보정 한계 입력, 색좌표 편집,
장면 저장/불러오기/앞으로 이동/삭제, 기존 5종 미리보기의 경로를 읽었다.
신규 E2E는 다중색·채택·되돌리기·출력·위치 충돌·Office XML 구조와
가로 overflow를 확인하는 코드를 포함한다. 이 리뷰는 테스트를 직접
실행하지 않았고 결과 통과를 별도로 주장하지 않는다.

브라우저 화면·터치 목표·실제 탭 순서·스크린리더 발화, 순차/발산/cyclic
엔진 수학, 출력 파일 외부 도구 가져오기, schema 파서 강건성, 실제 배포는
미검토다. 검토 중 발견한 사실을 신규 구현의 출시 완료로 간주하지 않았다.
