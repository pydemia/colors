## O1 — schema2 이행 뒤 코드 롤백의 데이터 복원이 정의되지 않음

- 중요도: 높음. 분류: 설계의 운영 실패 경계. 아직 새 구현의 재현된 결함은 아니다.
- 근거: `UPGRADE_SPEC.md:38` R15, `:74`–`:76`은 기존 저장 키를 유지하여
  schema1을 schema2로 이행한다. 기준 코드 `src/lib/project.ts:453`은
  schemaVersion 1만 읽고, `:596`은 저장 배열의 한 항목 파싱 실패로 전체
  불러오기를 실패시킨다. `:603`–`:608`의 저장도 먼저 전체 배열을 읽는다.
  `src/App.tsx:407`–`:418`은 편집 후 자동 저장한다.
- 실패조건 → 영향: 새 앱이 같은 키에 schema2를 쓰고 릴리스 장애로 이전
  코드를 다시 게시하면 이전 파서는 저장 목록을 읽지 못한다. 배포를
  되돌려도 사용자의 색·역할·장면 데이터는 이전 상태로 되돌아가지 않아
  복원과 새 저장이 함께 막힐 수 있다.
- 보호장치/반증: R15의 JSON 왕복과 잘못된 입력 차단, 현재의 저장 오류
  안내는 유효하다. 하지만 이미 작성된 schema2를 schema1 전용 릴리스가
  읽게 만들거나 이행 전 데이터를 복구하는 보호장치는 아니다. 수동 JSON
  백업만으로 자동 저장을 겪은 모든 기존 사용자의 복구를 보장하지 않는다.
- 최소 수정: 이행 전 원문 저장값을 별도 버전 키에 보존하고, 새 데이터
  검증/저장이 성공하기 전 원본을 덮어쓰지 않는 정책을 명시한다. 앱과
  데이터의 롤백을 각각 설명한다. schema2를 유지한 상태에서 안전한
  수정 릴리스를 배포하는 정책도 가능하나, 이전 코드로 단순 복귀하면
  데이터 호환이 회복된다는 주장은 하지 않는다.
- 검증 기준: schema1 복수 프로젝트 → schema2 편집/저장 → 재열기;
  저장 실패(예: quota 오류) 후 원본 보존; 손상/미래 버전 항목을 포함한
  저장소에서 다른 정상 데이터의 복구 경로; 이행 전 백업에서 ID·색·잠금·
  역할 override를 복원하는 테스트. 실제 코드 롤백 정책을 QA에 기록한다.

  이번에 할 수 없더라도 형식 산출 자체의 검증은 별도로 완료할 수 있다.

  안내를 구분한다. DTCG 소비 검증과 Figma 플러그인 호환, VS Code 설정

  표시한다. 미검증 호환성은 완료 주장에 넣지 않는다.
- 검증 기준: 각 출력이 현재 적용된 역할값에서 만들어지는지 다르게 수정한
  역할 fixture로 비교한다. DTCG와 Tailwind 3/4는 대응하는 독립 소비/파싱
  경로, ASE는 헤더·블록 길이·색 모델·채널 수·이름, Office는 XML 네임스페이스와

  검증한다. CUBE는 헤더, 33³ 행, 순서, domain, finite 채널, 독립 샘플
  평가를 검사한다. 실제 대상 도구를 열어 확인한 경우에만 제품/버전을 기록한다.

- 중요도: 중간. 분류: 출시 검증의 누락 가능성.
- 근거: `UPGRADE_SPEC.md:11`, `:40`, `:85`는 실제 도메인 확인을 요구한다.
  기존 `QA_REPORT.md:30`–`:35`에는 과거 배포 ID/빌드/공개 별칭의 테스트와

  로컬 dev 서버에 고정되어 있다. `e2e/flows.spec.ts:73`–`:97`의 저장 테스트는
  단일 고정색이고 새로운 다중색/유연색/위치 조건을 다루지 않는다.
- 실패조건 → 영향: 로컬의 새 기능 검사와 과거 QA 또는 별칭의 Ready 상태를
  합쳐 완료를 기록하면, custom domain에 실제 새 코드가 게시되었는지,
  기존 사용자 데이터가 새 코드에서 복원되는지 검증하지 못한다.
- 보호장치/반증: 새 명세는 프로덕션 핵심 흐름을 요구하므로 첫 화면/HTTP
  확인만으로 완료할 의도는 아니다. 다만 어떤 revision과 어떤 핵심 흐름을
  확인할지 기록 기준이 없으면 원래 10개 테스트의 재실행으로 대체할 수 있다.
- 최소 수정: 출시 QA에 `commit/빌드 식별값/deployment ID/custom domain/
  확인 시각/검증한 시나리오`를 남긴다. production baseURL로 동일하거나
  축약한 핵심 흐름을 실행할 수 있도록 검증 방식을 준비한다. 배포 실패 시
  이전 정상 deployment와 데이터 이행 정책(O1)을 함께 기록한다.
- 검증 기준: 실제 `colors.pydemia.ai`에서 복수 입력색의 부분 고정/제한
  보정 → 후보 적용 → 재생성 → schema1 가져오기 및 schema2 저장/재열기 →
  역할 수동 수정 → 현재 역할 출력값 일치를 확인한다. colormap의 고정 t
  평가/anchor 포함 CSV와 충돌 안내, 모바일 핵심 조작도 새 revision에서
  확인한다. 모든 R의 전체 시나리오를 프로덕션에서 반복하라는 요구는 아니다.

## 미검토와 판정의 한계

- 이번 리뷰는 설계와 기준 코드의 저장/QA 경계에 대한 독립 검토다.
  새 엔진·schema2·출력 인코더는 아직 구현 전이므로 runtime 품질을 판정하지 않았다.
- Google Docs의 원문 전체는 이번 독립 입력으로 다시 받지 않았다.
  사용자가 제공한 자료를 정리한 `COLOR_IMPROVEMENT_REVIEW.md` 및 저장소의
  원래 제품/릴리스 계획을 범위 추적 근거로 삼았다.
- 대상 Adobe/Office/편집기/터미널/영상 프로그램은 실행하지 않았다.
  실도구 호환성을 인증한 리뷰가 아니다.
- 새 production 배포, 도메인/캐시/인증 상태, 실제 브라우저 저장 복원은
  실행하지 않았다. 과거 QA의 성공 기록은 새 구현 검증 결과로 쓰지 않았다.
- 색채 수학, 심미성, 세부 인터랙션, 보안·인프라 전체는 책임 범위 밖이다.
  다른 persona의 결과와 대조하거나 판정을 합치지 않았다.
