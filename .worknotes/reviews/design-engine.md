### D1 — schema1의 수동 역할 연결을 migration에서 식별할 수 없다

- 분류·시점: 빠진 migration 계약 / 설계 선결. R11·R15의 수동 역할 유지에 직접 영향.
- 근거: 명세 51–52, 74–76행은 수동 수정 유지와 파생 역할만 재계산을 요구한다. 검토 문서 156행은 기존 수동 연결의 `reason:null` 문제를 이미 지적한다. 고정 HEAD `project.ts:134–135`, `364–372`의 `ref()`와 `setRoleSwatch()`는 자동 참조와 수동 참조 모두 `overrideHex:null, reason:null`을 만든다. `chooseCandidate():268–273`은 `userEdit`/`contrastAccepted`만 보존한다.
- 실패 시나리오: schema1에서 사용자가 `web.primary`를 `s5`에 연결하여 저장 → schema2 import 자체는 값 보존 → `reason:null`을 자동 연결로 이행 → 첫 재생성에서 기본 주색에 재연결. 가져오기는 성공했지만 사용자가 유지하려던 역할이 바뀐다.
- 보호장치의 반증: “override 그대로 이행”은 직접 HEX override에는 충분하지만, override가 없는 사용자 연결에는 충분하지 않다. 신규 schema2에서 수동 여부를 추가해도 기존 파일에는 그 정보가 없다. 기본 역할과 같은 참조인지 비교하면 일부 수동 수정만 찾을 수 있고 의도까지 복원하지는 못한다.
- 최소 수정: schema2에 자동/수동 연결의 명시적 구분을 두고, schema1 `reason:null` 참조는 보수적으로 legacy/manual 연결로 보존하는 등의 확정된 정책을 명세에 기록한다. import 시 기존 HEX/참조는 그대로 두고, 사용자에게 자동 연결 복구 동작을 제공할 수 있다. `reason:generated`는 import 즉시 색을 바꾸지 않고 이후 의존 갱신 정책에 따라 처리한다.
- 통과 기준: schema1 `web.primary={swatchId:'s5',overrideHex:null,reason:null}` 파일을 import → 후보 적용/재생성 → JSON 왕복한 뒤 `s5` 참조가 유지된다. `userEdit` 및 `contrastAccepted` HEX도 동일하며, 신규 자동 역할은 원본색 변화에 갱신된다.
- 미검증: schema2 parser/migration 구현과 실제 기기 저장 파일은 아직 실행 검증하지 않았다.

- 미검증: 어떤 schema2 결과 모델을 채택할지와 가변 결과 인코더는 아직 확인하지 않았다.

### D3 — colormap 유형별 성공 조건과 충돌 경로의 취급을 연결해야 한다

- 분류·시점: 빠진 함수/검증 계약 / 설계 선결. R12·R14의 유형 의미와 정확한 anchor 평가에 영향.
- 근거: 명세 35, 70–72행은 네 유형, 명시 stop, 충돌 표시를 요구한다. 검토 문서 269–275행은 순차형 명도 흐름, 발산형 중심 양쪽 흐름, 순환형 양끝 연결, 범주형 구분을 별도로 평가하고 290행은 고정된 cyclic 양끝 충돌을 명시한다. 현재 명세에는 발산 기준점/방향, cyclic seam, qualitative의 step/연속 여부 및 충돌 후 “유효한 유형” 판정이 없다.
- 실패 시나리오: (1) 두 다른 고정색이 `t=0.3`에 겹침 → 단일 함수가 두 anchor를 만족할 수 없는데 첫 stop만 선택. (2) cyclic의 고정된 `t=0/1`이 서로 다름 → 일반 보간을 출력하면서 cyclic 성공으로 표시. (3) sequential은 stop의 L만 정렬했지만 선택한 혼합·색역 처리 뒤 구간 안에서 L이 역전되어도 통과. (4) diverging/qualitative 선택이 이름만 바뀌고 같은 경로를 출력.
- 보호장치의 반증: 명세의 충돌 경고, 팔레트/함수 검사 분리 및 CSV union 정책은 중요한 보호장치다. 이는 각 유형의 의미와 경고가 붙은 경로를 유효한 추천/출력으로 판정해도 되는지까지 결정하지 않는다. CSV에 anchor 위치를 넣어도 같은 t의 서로 다른 색은 해결되지 않는다.
- 최소 수정: 유형마다 판정 계약을 둔다. sequential은 실제 t 순서에서 선언한 방향의 L 흐름, diverging은 저장한 중심과 양쪽 흐름, cyclic은 `f(0)=f(1)` 및 seam 평가, qualitative는 명시한 범주형 bucket/색 목록을 사용한다. 색/위치 잠금은 모두 검사 입력에 포함한다. 같은 t의 같은 색은 여러 ID 대응을 보존할 수 있지만 다른 고정색은 해결되지 않은 함수 충돌이다. 충돌이 있어도 프로젝트 보존은 가능하되 “유효한 해당 유형”으로 성공 표시하지 않는다.
- 통과 기준: 위 네 사례와 `t=0.3` anchor에서 실제 `f(t)`/CSV HEX의 정확 일치. 유형 검사는 최종 혼합·색역 결과의 구간 표본도 포함한다. 고정 명도 역전 또는 seam 충돌은 잠금색을 바꾸지 않고 표시하며, 사용자가 위치/유형/잠금 변경으로 해결하면 성공 상태가 바뀐다.
- 미검증: 모델별 경로 평가 샘플 수·허용 오차·범주 구분 휴리스틱은 구현에서 선언하고 검증해야 한다. 모든 모델에 지각 균등성을 보장할 수 있다는 주장은 하지 않는다.

### D4 — 좌표와 혼합의 계산 조건은 구현 전에 수치 계약으로 고정해야 한다

- 분류·시점: 조건부 위험 / 구현 검증으로 이관. R02·R06·R07·R15에 영향.
- 근거: 명세 29–30, 64, 67–68행은 여러 좌표와 선형 가색/투과율 곱을 정한다. 검토 문서 203, 211–225행은 Lab 백색점, hue 경로, 광량 합의 출력 매핑, 비율 끝점, 저장 조건을 요구한다. 이 구체 값은 아직 명세에 없다.
- 실패 시나리오: Lab 좌표를 D50로 표시하고 입력 변환을 D65로 처리하면 같은 숫자가 다른 HEX가 된다. 광량 합을 출력 범위에서 자르거나 평균으로 정규화하는 선택에 따라 동일 입력의 밝기가 달라진다. 단순 필터 곱 `A×B`는 혼합 비율과 무관하며, 비율을 쓰는 농도 보간은 0 채널의 끝점 처리가 필요하다. 무채색의 임의 hue를 ΔH 상한에 사용하면 보정이 잘못 막힐 수 있다.
- 보호장치의 반증: 선형 RGB 사용, 합/평균 구분, 감색의 근사 표시는 정확한 방향이다. 최종 HEX 상한 검증도 명세에 있어 양자화 후 과도한 보정 위험은 이미 보호한다. 남은 것은 계산 조건·단위·끝점의 동일성이다.
- 최소 수정: Lab/LCH 백색점과 변환 모드, hue 단위와 경로, 거의 무채색의 hue 판정 규칙, 합의 intensity/노출/클리핑 정책 및 필터 비율 공식을 구현 상수와 설명으로 선언한다. 좌표 표시 체계 전환은 색을 다시 생성하지 않고 편집 적용과 구분한다. 저장된 generator/model 버전으로 같은 연산을 재현한다.
- 통과 기준: 표시 체계만 여러 번 바꿔도 HEX 불변, 좌표 입력 왕복, 흰색/검정/회색 hue 처리, hue 359°↔1° 원형 차이, 평균의 양끝과 동일색 보존, 합의 동일색 밝기 증가 및 범위 초과 표시, 필터 비율 양끝/0채널 유한 결과, 최종 HEX의 보정 상한 모두 통과한다.
- 미검증: 현재 culori 설치 버전의 구체 변환 API와 새 구현의 수치 결과는 실행하지 않았다. 최신 API에 대한 주장은 이 보고서에 포함하지 않는다.

### D5 — LUT 출력은 팔레트 출력과 다른 보존·정확성 계약이 필요하다

- 분류·시점: 조건부 위험 / 구현 검증으로 이관. R01·R14의 출력 의미에 영향.
- 근거: 명세 16행은 별도 전체 RGB 룩 함수를 사용하고 37행은 33³ cube를 요구한다. 24행은 고정색 HEX가 “출력”에서 일치한다고 포괄적으로 기술한다. 검토 문서 130행의 LUT 설명과 명세 87–88행은 외부 영상 도구 검증까지 단정하지 않는다.
- 실패 시나리오: 고정색을 담은 팔레트의 몇 색을 33³ 배열로 반복하여 유효한 룩인 것처럼 출력하거나, 어떤 RGB 입력/전달함수에 적용되는지 모르는 LUT를 생성. 반대로 유효한 identity cube도 임의 고정색 `#123456`를 격자 entry에 직접 포함하지 않을 수 있으므로 팔레트의 anchor 포함 검사와 같은 검사를 적용하면 잘못 실패/성공 판정한다.
- 보호장치의 반증: 별도 전체 RGB 룩 함수라는 설계는 팔레트만으로 LUT가 유일하게 정해지는 오류를 이미 배제한다. 그러나 선택한 함수·입출력 조건과 R01의 고정색 보존이 LUT에서 무엇을 뜻하는지는 남아 있다.
- 최소 수정: LUT는 선언한 입력/출력 색공간과 전달함수에서 studio 조작을 적용하는 룩의 출력으로 정의하고, 팔레트/colormap의 고정 anchor 포함 계약과 구분한다. 필요한 경우 고정색이 그 룩에서도 그대로 유지되는지를 별도 함수 검증으로 보여 준다. 33³ 샘플 좌표와 행 순서, DOMAIN 및 정밀도를 명시하고 실제 도구 import 전에는 구조 검증 범위만 표시한다.
- 통과 기준: 35,937개의 유한 RGB 행, 선언한 범위와 순서, 무조작 identity 참조, 조작 전후 특정 입력색의 룩 함수와 cube sample 대응, 파일 재파싱/보간 검증. 팔레트의 모든 고정색 보존 검사는 계속 별도로 통과한다.
- 미검증: cube 인코더와 영상 도구 import는 아직 수행하지 않았다. 샘플 구조 검증을 실제 색 관리 호환성으로 확대 해석하지 않는다.

## 제외한 주요 의심과 미검토

- 고정색을 후보 뒤에 덮어쓰는 기존 `chooseCandidate()` 동작은 명세 65행에서 새 엔진 계약으로 명시적으로 금지했다. 기존 구현만으로 새 설계 결함이라고 중복 지적하지 않는다.
- 반복 보정의 누적 이동, 무채색의 조화 hue, 최종 sRGB 양자화 후 보정 상한, 피할 색과 잠금색의 충돌 표시, 실제 L과 Y의 구분, 필터/안료/ICC의 과학적 단정은 명세가 이미 보호한다.
- 256 균일 샘플에서 t=0.3 anchor가 빠지는 문제는 명세의 표본 union으로 해결한다. 고정 256행을 암묵적으로 보장하는 것으로 읽지 않는다.
- 사전 선언 없이 새 물리 광원·스펙트럼/ICC·유료 색표·AI API를 필수로 추가하지 않는다.
- 전체 앱 UI, 배포, 브라우저 접근성 및 외부 프로그램 import 검증은 이 persona의 실행 범위 밖이다. 테스트·빌드·브라우저 실행은 수행하지 않았다. 실패 시나리오는 설계상 재현 사례이며 실제 새 구현의 관측 결과가 아니다.
